## 0. Общая картина

**Задача.** Банк получает заявку на кредит. Нужно оценить **PD (probability of default)** —
вероятность, что клиент не вернёт кредит (просрочка 90+ дней в течение 2 лет), перевести её в
понятный балл 300–850 и принять решение «одобрить / отказать».

**Поток данных:**

```
make data   → скачать сырые данные → data/processed/dataset.parquet
make train  → split 80/20 → (Optuna + 5-fold CV) для 3 моделей → лучшая по CV
            → порог по матрице стоимости на OOF → метрики на test → SHAP
            → models/model.joblib + metadata.json, MLflow (run + Model Registry)
API         → POST /score: JSON → Pydantic → pipeline.predict_proba → PD → балл → решение
monitoring  → PSI между train и новой выборкой
```

Главный принцип: **всё, что учится на данных, учится только на train** и упаковано в один
sklearn `Pipeline` вместе с моделью. Этот же объект обслуживает API — нет расхождения между
тем, как признаки считались при обучении и при инференсе (training–serving skew).

## 1. Данные

**Что сделано.** `src/credit_scoring/data.py` скачивает и готовит данные одной командой
`make data`. Порядок источников (`dataset: auto` в `configs/config.yaml`):

1. Kaggle **Home Credit Default Risk** (`application_train.csv` + `bureau.csv`) — если есть Kaggle-токен;
2. Kaggle **Give Me Some Credit (GMSC)**;
3. зеркало GMSC на **OpenML** (id 46929) — без регистрации.

В этом запуске токена Kaggle не было, поэтому использован GMSC с OpenML: 150 000 заёмщиков,
10 признаков, доля дефолтов 6.68%. Код для Home Credit (агрегаты bureau, отношения сумм,
схема API) реализован и покрыт тестами на синтетических данных; переключение —
положить `~/.kaggle/kaggle.json` и снова выполнить `make data && make train`.

Данные **не коммитятся** (`data/` в `.gitignore`): они большие, у Kaggle есть лицензия на
распространение, и их всегда можно воспроизвести скриптом.

**Почему так.** Воспроизводимость: любой человек клонирует репозиторий и получает тот же
датасет одной командой. Fallback нужен, чтобы проект запускался и без Kaggle-аккаунта (CI, рекрутер).

**Альтернативы.** DVC для версионирования данных (уместно, когда данные меняются и их надо
хранить в S3); хранить небольшой sample в репозитории; читать прямо из банковского DWH через SQL.

**Вопросы на собеседовании:**

1. *Почему данные не лежат в git?* — Git не для больших бинарных файлов, история раздувается
   навсегда; плюс лицензия Kaggle. Данные воспроизводятся скриптом, в проде их версионируют
   через DVC/Delta Lake/снапшоты в DWH.
2. *Чем GMSC отличается от Home Credit?* — GMSC: одна таблица, 10 агрегированных признаков,
   150k строк. Home Credit: реляционные данные (заявка + кредитная история в бюро + платежи),
   300k заявок и 120+ признаков, поэтому важна агрегация «много строк на клиента → одна строка».
3. *Как бы вы получали данные в банке?* — SQL-витрина в DWH: заявка на дату решения + данные
   кредитного бюро (в Казахстане — ПКБ/ГКБ) **на дату заявки**. Ключевое — point-in-time
   корректность: нельзя брать данные, появившиеся после даты решения.
4. *Что такое target «дефолт»?* — В GMSC: просрочка 90+ дней в течение 2 лет после выдачи.
   Определение дефолта (90+ DPD) соответствует стандартам Базеля / МСФО 9.

## 2. EDA

**Что сделано.** `notebooks/01_eda.ipynb`: доля дефолтов, пропуски, распределения, проблемы
качества данных, зависимость дефолта от ключевых признаков, выводы.

Ключевые находки:
* **Дисбаланс**: 6.68% дефолтов (≈1:14).
* **Пропуски**: `monthly_income` — 19.8%, `dependents` — 2.6%. Пропуск информативен: без
  указанного дохода дефолтят *реже* (5.6% против 7.0%).
* **Качество данных**: в счётчиках просрочек встречаются коды **96/98** (это не «98 просрочек»,
  а служебные коды), `revolving_utilization` до 50 708 при норме 0..1, огромный `debt_ratio`
  там, где нет дохода (долг поделён на ~1), один заёмщик с `age = 0`.
* **Сильнейшие факторы**: количество просрочек (0 просрочек → 2.8% дефолтов, 6+ → 61%),
  утилизация кредитных карт (от ~2% до 23% по децилям), возраст (молодые рискованнее: 11% vs 2%).

**Почему так.** EDA определяет решения дальше: метрики под дисбаланс, обработку пропусков,
нужен ли winsorizing, ожидание нелинейностей → бустинг.

**Альтернативы.** Автоматические отчёты (ydata-profiling, sweetviz) — быстрее, но без выводов;
WoE/IV-анализ — классика банковских скоркарт (см. п. 17).

**Вопросы на собеседовании:**

1. *Как EDA повлиял на модель?* — Коды 96/98 превращены в NaN + флаг `delinquency_code`;
   для линейной модели добавлены winsorizing и индикаторы пропусков; метрики выбраны под
   дисбаланс; ожидание нелинейностей (утилизация × просрочки) → бустинги.
2. *Не утечка ли — смотреть на весь датасет в EDA?* — Нет, если ни одна статистика из EDA
   не попадает в модель. Все обучаемые преобразования (медианы, квантили) считаются в pipeline
   на train. В EDA мы только принимаем решения о *типе* обработки.
3. *Что делать с пропуском дохода?* — Не удалять строки (потеряем 20% данных и сместим
   выборку), а импутировать + оставить флаг пропуска: факт «доход не указан» сам несёт сигнал.
4. *Почему не удалили выбросы?* — Выбросы в кредитных данных часто реальны (и рискованны).
   Удаление строк меняет распределение; деревья устойчивы к выбросам, а для логрегрессии
   делаем winsorizing по квантилям train.

## 3. Признаки и защита от утечки данных

**Что сделано** (`src/credit_scoring/features.py`). Преобразования разделены на два типа:

**1. Stateless (построчные)** — зависят только от значений этой же строки, ничего не «учат»:

| Датасет | Признак | Смысл |
|---|---|---|
| GMSC | `total_past_due` | сумма всех просрочек 30–59, 60–89, 90+ |
| GMSC | `monthly_debt = debt_ratio × monthly_income` | ежемесячный платёж по долгам |
| GMSC | `income_per_person = income / (dependents + 1)` | доход на члена семьи |
| GMSC | `non_real_estate_lines` | кредитные линии кроме ипотеки |
| GMSC | `income_missing`, `delinquency_code` | флаги пропуска дохода и кодов 96/98 |
| Home Credit | `CREDIT_INCOME_RATIO` (кредит/доход), `ANNUITY_INCOME_RATIO` (аннуитет/доход), `ANNUITY_CREDIT_RATIO`, `GOODS_CREDIT_RATIO`, `EMPLOYED_AGE_RATIO`, `EXT_SOURCE_MEAN/MIN` | долговая нагрузка, срок, стаж |
| Home Credit | `BUREAU_*` (count/mean/max/sum по клиенту), `BUREAU_ACTIVE_COUNT/SHARE`, `BUREAU_DEBT_CREDIT_RATIO` | агрегаты кредитной истории из бюро |
| Home Credit | `DAYS_EMPLOYED = 365243 → NaN` + флаг | аномалия-заглушка для пенсионеров |

Агрегаты bureau: у клиента может быть много прошлых кредитов → `groupby(SK_ID_CURR)` →
count, mean/max дней с открытия, mean/max/sum суммы и долга, просрочки, число активных кредитов.
Клиент, которого нет в бюро, получает `BUREAU_LOAN_COUNT = 0`, но суммы остаются NaN
(«нет истории» ≠ «долг ноль»).

**2. Stateful (обучаемые)** — медианы для импутации, квантили для winsorizing, среднее/std для
скейлинга, словари категорий. Они **всегда внутри `sklearn.Pipeline`** и обучаются через `fit`
только на train-фолде:

* `linear` (для логрегрессии): `SimpleImputer(median, add_indicator=True)` → `QuantileClipper(1%, 99%)` →
  `StandardScaler`; категории — `OneHotEncoder(handle_unknown="infrequent_if_exist", min_frequency=0.01)`.
* `tree` (для бустингов): числа как есть (LightGBM/CatBoost сами обрабатывают NaN),
  категории — `OrdinalEncoder(unknown_value=-1)`.

**Почему так.** Построчные признаки безопасно считать до сплита: значение для клиента A не
зависит от клиента B. Всё, что использует статистику по многим строкам, при расчёте до сплита
«подсмотрит» test → оптимистичные метрики. Pipeline гарантирует, что при CV каждый фолд
обучает свои медианы/квантили, а в проде используется ровно тот же код.

**Как это проверено тестами** (`tests/test_leakage.py`):
* медиана импутера = медиане train, а не всего датасета; абсурдные значения в test не сдвигают границы;
* построчные признаки строки не меняются от того, какие ещё строки в батче;
* агрегаты bureau клиента не зависят от других клиентов и не содержат target;
* OOF-предсказание каждой строки сделано моделью, которая эту строку не видела
  (специальный «запоминающий» классификатор даёт 0 на всех OOF);
* target и ID не попадают в признаки.

**Альтернативы.** Featuretools (автоматическая агрегация), feature store (Feast) в проде,
target/WoE-encoding категорий (только out-of-fold, иначе утечка), больше агрегатов
(`bureau_balance`, `previous_application`, `installments_payments` в Home Credit).

**Вопросы на собеседовании:**

1. *Что такое утечка данных? Приведите примеры.* — Когда при обучении модель использует
   информацию, недоступную в момент реального решения. Примеры: импутация медианой всего
   датасета до сплита; target encoding без out-of-fold; признак, появившийся после выдачи
   (например, «количество звонков коллектора»); дубли клиента в train и test.
2. *Почему агрегаты bureau можно считать до сплита, а медиану — нет?* — Агрегат клиента
   использует только строки этого клиента (и они в бюро датированы до заявки). Медиана — это
   статистика по всем клиентам, включая test.
3. *Зачем `add_indicator=True`?* — Импутация медианой стирает факт пропуска. Индикатор
   сохраняет его как отдельный бинарный признак; в данных пропуск дохода связан с риском.
4. *Почему бустингам не нужна импутация?* — LightGBM/CatBoost на каждом сплите выбирают,
   в какую ветку отправлять NaN, т.е. учат оптимальную обработку пропуска.
5. *Почему OrdinalEncoder для деревьев и OneHot для логрегрессии?* — Деревья могут
   разрезать порядковые коды на любые группы; для линейной модели порядок кодов бессмысленен,
   нужен one-hot. Для высококардинальных признаков — CatBoost native categorical / target encoding.

## 4. Схема валидации

**Что сделано** (`train.py`):
1. Стратифицированный **hold-out 80/20**. Test (30 000 строк) используется **один раз** — для
   финального отчёта.
2. На train: **Stratified 5-Fold CV** → out-of-fold (OOF) предсказания для каждой модели.
3. **Лучшая модель выбирается по среднему CV ROC-AUC**, не по test.
4. **Порог** подбирается на OOF-предсказаниях train, затем проверяется на test.

**Почему так.** Если выбирать модель/порог по test, test перестаёт быть независимой оценкой
(мы «подогнали» решение под него). Стратификация сохраняет 6.7% дефолтов в каждом фолде —
при дисбалансе случайный сплит может дать фолды с заметно разной долей.

**Альтернативы.** **Out-of-time (OOT) валидация** — в банке стандарт: обучаемся на заявках
2022–2023, тестируемся на 2024. В GMSC нет дат, поэтому OOT невозможен. Group K-Fold — если
у клиента несколько заявок. Nested CV — честнее для оценки тюнинга, но дороже.

**Вопросы на собеседовании:**

1. *Зачем и CV, и hold-out?* — CV — для выбора модели и гиперпараметров (стабильная оценка с
   разбросом). Hold-out — независимая финальная оценка, которую не трогали при выборе.
2. *Что такое OOF-предсказания и зачем они?* — Предсказание для каждой строки train от модели,
   обученной без этой строки. Это «честные» предсказания на train: на них можно подбирать порог,
   калибровать, строить стекинг, не трогая test.
3. *Почему в банке важна out-of-time валидация?* — Модель применяется к будущим клиентам;
   экономика, продукты и маркетинг меняются (drift). Random split переоценивает качество.
4. *Разброс CV AUC ±0.003 — это много?* — Нет, это небольшая дисперсия (150k строк);
   разница моделей больше разброса, поэтому выбор устойчив.

## 5. Модели: baseline → LightGBM → CatBoost

**Что сделано.** Три модели в одинаковом pipeline:
* **Логистическая регрессия** — baseline: интерпретируемая, быстрая, «классика» скоркарт.
* **LightGBM** — градиентный бустинг, leaf-wise рост деревьев, очень быстрый.
* **CatBoost** — бустинг с симметричными (oblivious) деревьями и ordered boosting;
  устойчив к переобучению, нативно работает с категориями.

Классы **не перевзвешиваются** (`class_weight` / SMOTE не используются).

**Почему так.** Сначала baseline — чтобы понимать, сколько даёт сложность. Бустинги
ловят нелинейности и взаимодействия (утилизация × просрочки, возраст), это видно по +0.012 AUC.
Без перевзвешивания вероятности остаются **калиброванными**: банку нужна именно вероятность
(для порога, резервов по МСФО 9, ценообразования), а не только ранжирование.

**Альтернативы.** XGBoost (близок к LightGBM), Random Forest (обычно слабее бустинга),
нейросети (на табличных данных редко лучше бустинга, хуже интерпретируемость), стекинг
моделей, скоркарта на WoE + логрегрессия (регуляторный стандарт).

**Вопросы на собеседовании:**

1. *Чем LightGBM отличается от XGBoost и CatBoost?* — LightGBM: leaf-wise рост, гистограммы,
   GOSS — самый быстрый. XGBoost: level-wise, сильная регуляризация. CatBoost: симметричные
   деревья (быстрый инференс, меньше переобучение), ordered target statistics для категорий.
2. *Почему не SMOTE / class_weight при дисбалансе?* — Они искажают вероятности (модель
   завышает PD). Для ранжирования AUC почти не меняется, а калибровка ломается. Дисбаланс
   решается правильными метриками и порогом по стоимости ошибок.
3. *Зачем логрегрессия, если бустинг лучше?* — Baseline (сколько даёт сложность), sanity check
   пайплайна; в банке её проще валидировать и объяснить регулятору. Если выигрыш бустинга мал —
   часто выбирают логрегрессию.
4. *Как бороться с переобучением бустинга?* — Ограничить глубину/число листьев,
   `min_child_samples`, subsample/colsample, L1/L2-регуляризация, меньший learning rate +
   early stopping; контроль по CV.

## 6. Подбор гиперпараметров (Optuna)

**Что сделано.** Optuna с **TPE-сэмплером** (seed фиксирован) и **MedianPruner**:
LightGBM — 30 trials, CatBoost — 20 (лимит ≤ 30). Целевая функция — средний ROC-AUC на
3-fold CV на стратифицированной подвыборке 100k строк (экономия времени). Пространство поиска:
`n_estimators/iterations`, `learning_rate` (лог-шкала), `num_leaves`/`depth`,
`min_child_samples`, `subsample`, `colsample_bytree`, `reg_alpha/lambda`, `l2_leaf_reg` и др.
Pruner обрывает trial после первых фолдов, если он хуже медианы предыдущих.

**Почему так.** TPE (байесовская оптимизация) находит хорошие параметры за десятки итераций,
в отличие от grid search, который растёт экспоненциально. Тюнинг внутри train-CV не трогает test.

**Альтернативы.** GridSearchCV / RandomizedSearchCV, Hyperopt, Ray Tune; early stopping
вместо перебора `n_estimators`.

**Вопросы на собеседовании:**

1. *Как работает TPE?* — Делит прошлые trials на «хорошие» и «плохие», строит две плотности
   l(x) и g(x) и выбирает точки, где l(x)/g(x) максимально — т.е. похожие на хорошие.
2. *Почему random/bayes лучше grid?* — Grid тратит итерации на неважные параметры; random
   покрывает важные измерения лучше, bayes ещё и учится на прошлых результатах.
3. *Не переобучаемся ли мы на CV при тюнинге?* — Немного да (оптимистичная оценка лучшего
   trial), поэтому финальная оценка — на отложенном test, который тюнинг не видел.
4. *Зачем pruning?* — Экономит время: явно плохие конфигурации не досчитываются до конца.

## 7. Метрики и калибровка

**Что сделано** (`evaluate.py`): ROC-AUC, **Gini = 2·AUC − 1**, PR-AUC, **KS**, **Brier score**,
log-loss; графики calibration curve (`reports/calibration.png`) и ROC (`reports/roc.png`).

* **ROC-AUC** — вероятность, что случайный дефолтер получит PD выше, чем случайный хороший клиент.
* **Gini** — та же метрика в шкале, принятой в банках (0 — случайно, 1 — идеально).
  Gini 0.74 — очень хороший уровень для скоринга заявок.
* **PR-AUC** — качество на редком классе; baseline = доля дефолтов (0.067).
* **KS** — максимальное расстояние между распределениями PD хороших и плохих; стандарт в банках.
* **Brier** — среднеквадратичная ошибка вероятности; калибровка — совпадает ли
  предсказанный PD с наблюдаемой долей дефолтов.

**Почему так.** При дисбалансе accuracy бессмысленна. Банку нужны: ранжирование (AUC/Gini/KS)
и точные вероятности (Brier, calibration) — PD идёт в расчёт ожидаемых потерь EL = PD × LGD × EAD.

**Альтернативы.** Изотоническая / Platt калибровка (`CalibratedClassifierCV`) — если калибровка
плохая; Expected Calibration Error; lift/gain charts; метрики по бакетам скорбалла.

**Вопросы на собеседовании:**

1. *Что такое Gini и как он связан с AUC?* — Gini = 2·AUC − 1. AUC 0.87 ⇔ Gini 0.74.
2. *Что такое KS и какие значения хорошие?* — max(TPR − FPR) по порогам. 0.4–0.6 — хорошая
   скоринговая модель; > 0.75 — подозрение на утечку.
3. *Почему важна калибровка?* — Порог по стоимости, резервы (МСФО 9), ценообразование
   (risk-based pricing) используют PD как вероятность. AUC калибровку не проверяет.
4. *Почему PR-AUC ниже 0.5 — это плохо?* — Нет: baseline PR-AUC = доля позитивов (0.067),
   модель даёт ~0.41, т.е. в ~6 раз лучше случайной.
5. *Как улучшить калибровку?* — Isotonic/Platt на OOF-предсказаниях; не использовать
   перевзвешивание классов; проверять калибровку по времени.

## 8. Интерпретация (SHAP)

**Что сделано** (`explain.py`): `shap.TreeExplainer` для бустинга (`LinearExplainer` для
логрегрессии) на 2000 клиентах test:
* `reports/shap_summary.png` — глобальная важность и направление влияния признаков;
* `reports/shap_client.png` — waterfall для одного клиента (95-й перцентиль риска):
  какие признаки и насколько увеличили его PD;
* `reports/feature_importance.csv` — mean |SHAP|; `metrics.json` — топ-причины клиента.

**Почему так.** Банк обязан объяснить отказ клиенту и регулятору (reason codes / adverse
action). SHAP даёт аддитивное разложение: base value + сумма вкладов = log-odds модели.

**Альтернативы.** Встроенный feature importance (split/gain — смещён к признакам с большим
числом уникальных значений), permutation importance, LIME (нестабилен), PDP/ICE, монотонные
ограничения в бустинге, WoE-скоркарта (интерпретируема «по построению»).

**Вопросы на собеседовании:**

1. *Что такое SHAP value?* — Вклад признака в предсказание по теории игр (вектор Шепли):
   средний маржинальный вклад по всем порядкам добавления признаков. Сумма вкладов +
   base value = выход модели (здесь — log-odds дефолта).
2. *Чем SHAP лучше feature_importance_ из LightGBM?* — Он локальный (для каждого клиента),
   показывает направление, согласован (consistency), не смещён к высококардинальным признакам.
3. *Как объяснить отказ клиенту?* — Взять топ-3 признака с наибольшим положительным SHAP
   для клиента и перевести в текст: «высокая загрузка кредитных карт», «были просрочки 30–59 дней».
4. *Корректна ли модель с точки зрения бизнеса?* — По SHAP: выше утилизация и больше
   просрочек → выше риск, старше возраст → ниже риск. Это совпадает с экспертной логикой.
   Если нет — повод искать утечку или добавить монотонные ограничения.

## 9. Бизнес-порог по матрице стоимости

**Что сделано.** Две ошибки имеют разную цену (`configs/config.yaml → business`):
* **FN** — одобрили, клиент ушёл в дефолт: теряем `loan × LGD = 500 000 × 0.6 = 300 000 ₸`;
* **FP** — отказали хорошему клиенту: теряем процентный доход `loan × margin = 500 000 × 0.12 = 60 000 ₸`.

Пропуск дефолта в **5 раз дороже**. Порог выбирается перебором по сетке на **OOF-предсказаниях**
train, минимизируя ожидаемую стоимость на заявку; затем на test считаются approval rate, доля
дефолтов среди одобренных и ожидаемые потери на 1000 заявок (`reports/cost_curve.png`).
Сравнение с политиками «одобрить всех» и «порог 0.5» — в README.

**Теория.** Для калиброванного PD одобрять выгодно, если `PD × C_FN < (1 − PD) × C_FP`,
т.е. `PD < C_FP / (C_FP + C_FN) = 1/6 ≈ 0.167`. Эмпирический порог близок к теоретическому —
ещё одно подтверждение хорошей калибровки.

**Почему так.** Порог 0.5 бессмыслен при доле дефолтов 6.7%: почти все PD ниже 0.5, банк
одобрит практически всех, включая рискованных. Порог — **бизнес-решение**, а не свойство модели.

**Альтернативы.** Порог под целевой approval rate или целевой bad rate (risk appetite);
три зоны: auto-approve / ручной андеррайтинг / auto-decline; risk-based pricing вместо
бинарного решения (ставка зависит от PD); учёт EAD/суммы кредита конкретного клиента.

**Вопросы на собеседовании:**

1. *Почему не порог 0.5?* — 0.5 оптимален только при равной цене ошибок и балансе классов.
   У нас FN в 5 раз дороже, оптимум около 1/6.
2. *Почему порог подбирается на OOF, а не на test?* — Иначе test перестаёт быть независимой
   оценкой: мы подгоним порог под него и завысим бизнес-результат.
3. *Что такое approval rate и bad rate?* — Доля одобренных заявок и доля дефолтов среди
   одобренных. Это основной компромисс в рознице: больше одобряем — больше выручка и больше риск.
4. *Откуда LGD = 0.6?* — Допущение для беззалоговой розницы (типично 0.45–0.75);
   в банке берётся из модели LGD / статистики взыскания. Параметры вынесены в конфиг.
5. *Как учесть сумму кредита?* — Ожидаемая потеря клиента EL = PD × LGD × EAD; решение
   «одобрить, если ожидаемая прибыль > EL» считается для каждой заявки.

## 10. Скоринговый балл 300–850

**Что сделано** (`predict.py → ScoreCard`). Классическое масштабирование «points to double odds»:

```
odds  = (1 − PD) / PD                 # шансы «хороший : плохой»
factor = PDO / ln(2),  offset = base_score − factor × ln(base_odds)
score = clip(offset + factor × ln(odds), 300, 850)
```

Параметры: 650 баллов при шансах 50:1, **+40 баллов удваивают шансы** (PDO). Выше балл → ниже риск.

**Почему так.** Балл понятнее бизнесу и клиенту, чем вероятность; шкала линейна по log-odds,
поэтому «+40 баллов» везде означает одно и то же. Тесты проверяют: PD = 1/51 → ровно 650,
монотонность, границы.

**Альтернативы.** Балл из WoE-скоркарты (сумма баллов по атрибутам), рейтинговые грейды
(AAA…D, бакеты по PD), перцентильная шкала.

**Вопросы на собеседовании:**

1. *Что такое PDO?* — Points to Double the Odds: на сколько баллов надо вырасти, чтобы шансы
   «хороший:плохой» удвоились.
2. *Почему log-odds, а не линейно от PD?* — Логистическая модель линейна в log-odds;
   балл становится аддитивным, и разница баллов имеет одинаковый смысл по всей шкале.
3. *Можно ли сравнивать баллы разных моделей?* — Только если обе калиброваны и используют
   одинаковые base score / odds / PDO. После переобучения балл должен сохранять смысл —
   поэтому важна калибровка.

## 11. MLflow: трекинг и реестр моделей

**Что сделано.** Каждый `make train` — родительский run `training-<dataset>` с вложенными
run-ами на каждую модель. Логируются параметры (включая найденные Optuna), CV/test метрики,
время, все отчёты/графики как артефакты. Лучший pipeline логируется через
`mlflow.sklearn.log_model` с **signature** и input example и **регистрируется в Model Registry**
(`credit-scoring-pd`) с алиасом **`champion`**. Backend — SQLite (`mlflow.db`); в
docker-compose — отдельный MLflow server с проксированием артефактов.

MLflow 3 сериализует sklearn-модели через **skops** и отказывается загружать «недоверенные»
классы. Мы явно передаём список типов собственного pipeline (`_own_types`) — модель
создана нашим кодом, поэтому эти типы доверенные.

**Почему так.** Воспроизводимость и сравнение экспериментов; реестр — единый источник правды
«какая модель сейчас в проде». Алиасы (`champion`/`challenger`) заменили устаревшие stages.

**Альтернативы.** Weights & Biases, Neptune, ClearML, DVC experiments; деплой модели из
реестра (`models:/credit-scoring-pd@champion`) вместо файла `models/model.joblib`.

**Вопросы на собеседовании:**

1. *Что логировать в MLflow?* — Параметры, метрики, версию данных/кода (git commit),
   артефакты (графики, модель, signature), окружение (requirements).
2. *Зачем Model Registry?* — Версионирование моделей, алиасы для прод/кандидата, история,
   кто и когда перевёл, откат на предыдущую версию.
3. *Что такое signature?* — Схема входа/выхода модели; MLflow проверяет входные данные при
   serving. Целые колонки объявлены как float, иначе пропуск на инференсе сломает схему.
4. *Почему pickle — риск и что такое skops?* — Загрузка pickle выполняет произвольный код;
   skops сохраняет модель в безопасном формате и загружает только разрешённые типы.

## 12. API на FastAPI

**Что сделано** (`api/`):
* `POST /score` → `{probability_default, score, decision, threshold, model_version}`;
* `GET /health` → статус, загружена ли модель, версия; `503`, если модели нет;
* Pydantic-схема запроса: типы и диапазоны (`age` 18–120, неотрицательные суммы,
  `extra="forbid"`) → неверный запрос получает **422** до обращения к модели;
* модель загружается один раз при старте (`create_app`), схема выбирается по датасету модели;
* Swagger UI автоматически на `/docs`.

**Почему так.** FastAPI — стандарт для ML-сервисов на Python: валидация через Pydantic,
OpenAPI-документация, высокая производительность (ASGI/uvicorn). Фабрика `create_app()`
позволяет в тестах подменять каталог модели.

**Альтернативы.** Flask (нет встроенной валидации), BentoML / MLflow serving / Seldon / KServe,
gRPC для низкой латентности, батч-скоринг через Spark для массовых расчётов.

**Вопросы на собеседовании:**

1. *Что будет, если прислать age = 10 или лишнее поле?* — 422 Unprocessable Entity с описанием
   ошибки; модель не вызывается.
2. *Почему модель загружается при старте, а не на каждый запрос?* — Загрузка — сотни
   миллисекунд; при старте — один раз, запрос занимает миллисекунды.
3. *Как масштабировать сервис?* — Несколько воркеров uvicorn, горизонтальное масштабирование
   контейнеров за балансировщиком (Kubernetes HPA), модель stateless.
4. *Что ещё нужно для прода?* — Аутентификация, логирование запросов и предсказаний
   (для мониторинга и аудита), метрики Prometheus, rate limiting, версионирование API.
5. *Зачем `/health`?* — Liveness/readiness probes в Docker/Kubernetes: не отправлять трафик
   в контейнер, где модель не загрузилась.

## 13. Docker и docker-compose

**Что сделано.** `Dockerfile`: `python:3.12-slim`, `libgomp1` (нужен LightGBM), установка
пакета без dev-зависимостей, непривилегированный пользователь, `HEALTHCHECK`, uvicorn с 2
воркерами. Модель монтируется томом `./models:/app/models:ro`. `docker-compose.yml`:
сервисы `api` (порт 8000) и `mlflow` (tracking server, порт 5000, SQLite + артефакты в volume).

**Почему так.** Одинаковое окружение везде («у меня работает» → «везде работает»).
Slim-образ меньше и безопаснее; сначала копируются зависимости → кэш слоёв при изменении кода.
Модель томом — можно обновить модель без пересборки образа. Версии sklearn/LightGBM/CatBoost
закреплены (`~=`), потому что pickle-модель должна загружаться той же версией библиотек.

**Альтернативы.** Запекать модель в образ (иммутабельный артефакт — тоже хороший вариант для
прода), multi-stage build, distroless-образы, загрузка модели из MLflow Registry при старте.

**Вопросы на собеседовании:**

1. *Зачем non-root пользователь?* — Если сервис взломают, у атакующего не будет root внутри контейнера.
2. *Почему порядок COPY важен?* — Docker кэширует слои: зависимости меняются редко, код
   часто; если копировать код раньше, каждый коммит переустанавливает все пакеты.
3. *Модель в образе или в томе?* — В образе: неизменяемый артефакт, простой откат по тегу.
   В томе/реестре: обновление без пересборки. В проде чаще — образ с конкретной версией модели
   или загрузка по алиасу из реестра.
4. *Как обратиться к MLflow из обучения?* — `MLFLOW_TRACKING_URI=http://localhost:5000 make train`.

## 16. Мониторинг дрейфа (PSI)

**Что сделано** (`drift.py`, `make drift`). **Population Stability Index** по ключевым признакам
между train (reference) и новой выборкой:

```
PSI = Σ (cur% − ref%) × ln(cur% / ref%)
```

Бины — децили train (границы учатся на reference), NaN — отдельный бин. Пороги:
< 0.10 стабильно, 0.10–0.25 умеренный сдвиг, > 0.25 значимый → кандидат на переобучение.
Демо: train vs hold-out (дрейфа нет, все PSI ≈ 0) и hold-out с искусственным сдвигом
(«новый канал привлечения»: доход −25%, возраст −7 лет, утилизация ×1.4) →
`reports/drift_report.md`.

**Почему так.** PSI — стандарт банковского мониторинга, легко объяснить риск-менеджерам.
Метки дефолта приходят через месяцы (90+ дней просрочки), поэтому дрейф входных данных — ранний
сигнал деградации.

**Альтернативы.** KS-тест / Wasserstein distance, Evidently AI / NannyML, мониторинг PSI самого
скорбалла, CSI, отслеживание approval rate и, когда приходят метки, Gini по поколениям выдач (vintage).

**Вопросы на собеседовании:**

1. *Как считается PSI и какие пороги?* — См. формулу; < 0.1 / 0.1–0.25 / > 0.25.
2. *Data drift vs concept drift?* — Data drift: меняется распределение X (пришли другие клиенты).
   Concept drift: меняется связь X → y (кризис: те же клиенты дефолтят чаще). Второй виден
   только по меткам.
3. *Что делать при PSI > 0.25?* — Разобраться в причине (ошибка в данных? новый продукт?
   изменение маркетинга?), проверить качество на свежих метках, при необходимости переобучить.
4. *Почему границы бинов по reference?* — Иначе бины «подстроятся» под новую выборку и сдвиг
   будет недооценён; так же фиксируется эталон.

## 17. Ограничения и что улучшить

* **Out-of-time валидация** — в GMSC нет дат; на реальных данных — обязательна.
* **Home Credit с полной реляционной схемой** (`bureau_balance`, `previous_application`,
  `installments_payments`) — запустить с Kaggle-токеном.
* **WoE / IV скоркарта** как регуляторный baseline; монотонные ограничения в LightGBM.
* **Reject inference** — модель учится только на одобренных клиентах (selection bias).
* **Калибровка** isotonic/Platt на OOF и проверка по времени.
* **Reason codes в API** (топ-3 SHAP-причины отказа).
* **Fairness-анализ** (возраст как признак — регуляторный вопрос: допустим ли он для решения).
* **Champion/challenger** и A/B-тест порога; three-zone decision (ручной андеррайтинг).
* **Масштабирование**: PySpark для фич на больших объёмах, батч-скоринг, feature store.
* **Мониторинг в проде**: логирование запросов, Prometheus/Grafana, алерты по PSI.

## 18. Шпаргалка: проект за 60 секунд

> «Я сделал модель PD для розничного кредитования. Данные — 150 тыс. заёмщиков с долей
> дефолтов 6.7%. Признаки — построчные отношения (долговая нагрузка, доход на члена семьи,
> суммарные просрочки) и, для Home Credit, агрегаты кредитной истории из бюро; всё обучаемое —
> внутри sklearn Pipeline, утечка проверена тестами. Сравнил логрегрессию, LightGBM и CatBoost
> на stratified 5-fold CV с Optuna; лучшая модель даёт Gini ≈ 0.74 и KS ≈ 0.59 на отложенной
> выборке и хорошо откалибрована. Порог выбрал по матрице стоимости — пропуск дефолта в 5 раз
> дороже отказа хорошему клиенту, — он близок к теоретическому 1/6. SHAP объясняет решения
> глобально и для отдельного клиента. Всё логируется в MLflow с реестром моделей, модель
> обслуживается FastAPI-сервисом в Docker, есть CI с тестами и мониторинг дрейфа через PSI.»
